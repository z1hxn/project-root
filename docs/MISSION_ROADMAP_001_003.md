# PROJECT ROOT — 도입 및 MISSION 001–003 설계안

> **현재 구현 순서 (2026-10-17):** 사용자의 요청으로 「워크스테이션 둘러보기」를 MISSION 001로 복구했다. 아래는 복구 이전에 작성된 기획 초안이므로 본문의 사건 번호는 현재 게임보다 하나씩 앞선다. 현재 MISSION 002는 「사라진 링크」, MISSION 003은 「새벽의 빌드 알림」, MISSION 004는 「비정상 접근 기록」이다. MISSION 001은 Firefox에서 PROJECT ROOT 공식 사이트를 열면 완료되고 약 20초 후 다음 임무가 배정된다. 진행 상태 버전 2의 계정은 번호, 대기 단계, 힌트를 새 순서로 이관한다.

> 상태: 기획 초안. 현재 구현 상태를 설명하는 문서가 아니라, 다음 개편의 목표 설계다.  
> 기준: `PROJECT_ROOT_CONCEPT_v2.md`의 점진적 세계관 확장과 `PROJECT_ROOT_MISSION_002_CONTENT_PACK`의 사건 자료를 함께 사용한다.

## 1. 이번 개편의 결정

현재 **MISSION 001 「워크스테이션 둘러보기」**는 종료 조건이 없는 자유 탐색이다. 이는 사건이라기보다 조작 도입에 가깝다. 현재 **MISSION 002 「비정상 접근 기록」**은 첫 실제 조사에서 내부 문서, SMB, 패키지 설치, 여러 로그, 공개 웹, 긴 보고서를 한꺼번에 요구한다. 두 임무 사이에 학습 단계가 없고, 무엇을 하면 다음 단계로 넘어가는지도 불명확하다.

개편 후에는 세계관 안내 직후 **번호 없는 도입: 워크스테이션 적응**을 제공하고, 해결 가능한 사건 세 개를 순서대로 배정한다. 현재의 비정상 접근 콘텐츠는 **MISSION 003**의 핵심 자료로 보존한다. 기존 번호와 저장 데이터는 구현 시 명시적으로 이관한다.

| 구간 | 사건 | 플레이 시간 목표 | 필수 도구 | 새로 배우는 판단 | 세계관에서 보이는 것 |
| --- | --- | --- | --- | --- | --- |
| 도입 | 워크스테이션 적응 | 3–5분 | Project Root, Firefox 또는 Dolphin | 앱 이동과 자료 열기 | 조사관의 평범한 업무 공간 |
| MISSION 001 | 사라진 링크 | 10–15분 | KMail, Firefox, Project Root | 오래된 주소와 최신 출처 구별 | 공개 기록을 다루는 조직과 윤서하의 이름 |
| MISSION 002 | 새벽의 빌드 알림 | 15–25분 | Dolphin, Project Root; Konsole은 선택 | 시간·계정·작업 유형을 두 기록에서 대조 | 내부 문서와 자동화 시스템 |
| MISSION 003 | 비정상 접근 기록 | 25–40분 | Dolphin, Konsole, Firefox, Project Root | 정상 패턴과 이탈을 비교하고 결론의 한계 표시 | 내부 접근 기록과 조직의 더 큰 의문 |

플레이 시간은 난이도 조정을 위한 목표치이며 제한 시간이 아니다. 검색 엔진이나 터미널 명령에 대한 사전 지식은 필요하지 않다. 게임 안에서 필요한 정보에 도달할 수 있어야 한다.

## 2. 세 임무에 공통으로 적용할 규칙

1. **사건은 질문으로 시작한다.** 사건 화면은 `무엇을 판단할지`, `처음 확인할 자료`, `제출할 결과`를 보여준다. 정답 주소나 결론은 바로 알려주지 않는다.
2. **모든 필수 단서는 배정 시점에 접근 가능하다.** 잠긴 페이지, 구현되지 않은 명령, 실제 인터넷 검색이 해결의 필수 조건이 되면 안 된다. 막힌 경로는 이용 가능한 대체 경로나 그 이유를 설명한다. 완료 후 다음 임무까지의 짧은 대기는 풀이 조건과 구분한다.
3. **필요한 행동과 증거를 구분한다.** 단순 방문·앱 열기는 학습 진도로 표시할 수 있지만, 정답은 자료 내용의 비교에서 나온다. 우연히 정답 문자열을 입력했다고 조사 완료로 처리하지 않는다.
4. **보고서는 증거 선택과 짧은 이유로 구성한다.** 게임에서 발견한 문서·페이지·로그를 선택하거나 첨부하고, 한두 문장으로 판단을 적는다. 날짜·파일명·URL을 정확히 외워 다시 입력하게 하지 않는다. 자유 서술은 설명용이지 숨겨진 문자열 검사 대상이 아니다.
5. **힌트는 현재 막힌 단계에 맞춘다.** 각 단계에서 `방향 → 위치/도구 → 실행 가능한 다음 행동` 순서로 제공한다. 마지막 힌트는 실제로 실행할 수 있는 경로를 가리킨다. 힌트 사용은 실패나 감점으로 취급하지 않는다.
6. **진행 상태를 볼 수 있게 한다.** 사건 화면에는 `확인한 자료`, `남은 질문`, `제출 전 확인 사항`을 표시한다. 올바른 증거를 확보하면 즉시 반영하고, 잘못된 제출은 어느 판단이 부족한지 알려준다.
7. **되돌아가도 막히지 않는다.** 다시 플레이할 때 임무 자료와 필수 권한을 재구성한다. 기존 개인 메모와 파일을 유지하더라도 이전 조사 결과가 새 플레이의 완료 조건을 건너뛰게 해서는 안 된다.

### 난이도를 올리는 방식

- MISSION 001: **두 출처에서 한 가지 사실 확인**. 눈에 띄는 오래된 결과 하나를 걸러낸다.
- MISSION 002: **세 기록에서 한 가지 원인 분류**. 같은 시각이라는 이유만으로 사람의 접속으로 단정하지 않는다.
- MISSION 003: **여러 기록의 패턴 비교와 불확실성 평가**. 내부 기록을 먼저 확보하고 공개 기록은 마지막에 교차검증한다.

도구 조작의 복잡도와 추론의 복잡도를 동시에 크게 올리지 않는다. MISSION 002에서는 내부 기록을 읽는 방법을 익히고, MISSION 003에서 가상 SMB 접근을 추가한다.

## 3. 번호 없는 도입 — 워크스테이션 적응

세계관 안내 후 Project Root가 열리며 `자료는 Project Root, Firefox, Dolphin에서 확인할 수 있다`는 짧은 안내를 보여준다. 플레이어는 **Firefox 또는 Dolphin 중 하나**에서 예시 자료를 열어 본 뒤 `첫 사건 받기`를 누를 수 있다. 열기 행동은 체크되지만, 다른 앱을 모두 열거나 일정 시간을 기다릴 필요는 없다.

도입은 건너뛰고 나중에 다시 볼 수 있다. 현재의 「워크스테이션 둘러보기」 문구와 안내 기능은 이 구간으로 옮긴다. 이 행동을 `MISSION 001 완료`로 기록하지 않는다.

## 4. MISSION 001 — 사라진 링크

### 플레이어에게 보이는 사건

> 공개 자료 목록에서 오래된 링크 하나가 열리지 않습니다. 자료가 삭제된 것인지, 새 주소로 옮겨진 것인지 확인하고 현재 참조할 주소를 기록해 주세요. 같은 제목의 검색 결과가 여러 개 있으니 게시 주체와 갱신 시각을 함께 확인하세요.

업무 메일에는 **자료 제목**, **옛 주소**, **마지막 확인 시점**이 있다. Project Root 사건 화면에는 `현재 유효한 공개 주소를 찾고, 옛 주소와의 관계를 판단하라`는 목표가 있다. 클릭 가능한 옛 주소와 Firefox 검색 입력 경로를 함께 제공한다. 메일 본문에서 복사/붙여넣기도 가능해야 한다.

### 필요한 자료와 플레이 경로

| 자료 | 위치 | 플레이어가 얻는 정보 |
| --- | --- | --- |
| 업무 요청 | KMail 받은 편지함 | 자료 제목과 옛 주소. 처음 열 자료가 명확하다. |
| 옛 주소 | Firefox 가상 웹 | 서비스 자체의 404/이동 안내. 단순 네트워크 오류가 아니다. |
| 현재 공개 자료 | Firefox의 Google 검색 또는 공식 사이트 탐색 | 동일한 자료의 새 주소와 갱신 시각. 직접 주소 입력만이 유일한 경로가 아니다. |
| 변경 이력 | 가상 GitHub의 관련 공개 저장소/이슈 | 옛 주소가 새 주소로 교체됐다는 독립적인 기록. |
| 혼동 결과 | 검색 결과 한 개 | 제목이 비슷하지만 게시 주체나 시점이 달라 선택할 수 없다. |

권장 경로: **메일 확인 → 옛 주소 열기 → 자료 제목으로 검색 → 현재 페이지 확인 → 변경 이력 대조 → 간단한 확인 보고**. 검색을 먼저 해도, 공식 사이트에서 탐색해도 해결된다. 정확한 문자열 검색어 하나에 의존하지 않도록 제목의 핵심 단어·주소 일부·조직명으로 검색 결과를 찾을 수 있게 한다.

### 정답과 완료 조건

- 판단: **삭제나 침해로 단정할 근거가 없고, 공식 자료 주소가 갱신되었다.**
- 제출: 새 공식 주소 하나, 변경을 뒷받침하는 공개 이력 하나, `주소 이동/갱신` 선택과 한 문장 설명.
- 증거 조건: 게임에서 실제로 열어 본 현재 페이지와 변경 이력을 선택해야 한다. 옛 주소 404만 보고 제출하면 `새 주소와 변경 기록을 확인해 주세요`라고 안내한다.
- 결론은 객관식으로 고르되, 그 근거 자료를 구분해야 하므로 링크 하나 클릭하는 문제로 끝나지 않는다.

### 단계별 힌트

1. “옛 주소가 열리지 않는다는 사실만으로 자료가 삭제됐다고 판단할 수는 없습니다.”
2. “메일에 적힌 자료 제목으로 Firefox에서 검색하고 게시 주체를 확인해 보세요.”
3. “현재 공식 페이지의 갱신 시각과 공개 변경 이력에서 옛 주소를 비교하세요.”

### 세계관과 다음 임무

공개 변경 이력에는 **윤서하**라는 기여자 이름과 `index` 관련 작업명이 자연스럽게 등장한다. 이 시점에서는 수상한 사람으로 제시하지 않는다. 사건을 마치면 Project Root가 `출처를 확인해 기록을 바로잡았다`고 피드백하고, 약 20초의 완료 대기 화면 후 내부 운영 기록을 다루는 MISSION 002를 배정한다.

### 새로 만들어야 할 콘텐츠

KMail 사건 메일, 옛 주소의 서비스 수준 404/이동 안내, 현재 공식 자료 페이지, 검색 결과와 무관한 유사 결과, GitHub 변경 이력, 간단 보고 UI가 필요하다. 현재 가상 웹은 공식 사이트 루트만 제공하므로 하위 페이지와 검색 인덱스를 추가해야 한다. **자료의 제목과 실제 URL은 콘텐츠 제작 때 한 fixture에서 확정**하고 다른 곳에 중복 하드코딩하지 않는다.

## 5. MISSION 002 — 새벽의 빌드 알림

### 플레이어에게 보이는 사건

> 개발 환경에서 새벽 01:30에 발생한 접근 알림을 검토해 주세요. 사용자 접속인지 예정된 자동 작업인지 현재 제공된 운영 기록으로 분류하고, 판단 근거 두 가지를 제출하세요.

이는 MISSION 003의 복잡한 인증 사건을 풀기 전에 **자동 작업과 사용자 활동을 구별하는 연습**이다. `새벽 활동 = 침입`이라는 추측을 꺾되, 범위를 한 시각과 한 계정으로 제한한다.

### 필요한 자료와 플레이 경로

| 자료 | 위치 | 플레이어가 얻는 정보 |
| --- | --- | --- |
| 사건 카드 | Project Root | 확인할 시각 `2026-09-26 01:30 KST`와 계정 `svc-build`. |
| 운영 안내 | Dolphin → Network → PROJECT ROOT → Documentation의 입문 문서 | `svc-` 계정이 자동 작업에 쓰일 수 있다는 일반 원칙과 기록 위치. |
| 작업 기록 | Dolphin의 사건용 읽기 전용 내보내기 폴더 | `nightly-index-build`, `build-runner-02.root.internal`, 시작·종료 시각. |
| 일정 기록 | 같은 사건용 폴더 | 예약된 `nightly-build` 작업과 같은 runner, 완료 결과. |
| 인증 발췌 | 같은 사건용 폴더 | `svc-build`, `service-token`, `artifact-store`와 동일 시각. |

이 사건용 자료는 **Dolphin에서 모두 읽을 수 있는 묶음**으로 제공한다. 현재 콘텐츠 팩의 `build/build-runner.log`, `application/scheduler.log`, `auth/auth-2026-09-26.log`에서 필요한 부분을 쓰되, 원본 전체 로그와 SMB 접속은 MISSION 003에서 연다. Konsole의 `cat`·`grep`으로 같은 자료를 읽는 것은 허용하지만 필수로 하지 않는다. `01:30`을 자동 작업이라고 문서 한 줄이 직접 답하지 않게 한다.

### 정답과 완료 조건

- 판단: **제공된 01:30 알림은 예약된 `svc-build` 빌드 작업과 일치한다.** `이 사건에서 승인되지 않은 사용자 접속을 확인했다`는 결론은 지원되지 않는다.
- 제출: 분류 `예정된 자동 작업`, 작업 기록과 일정 기록 각각 하나, 인증 발췌의 계정/인증 방식 확인, 짧은 설명.
- `01:30` 사건만 종료한다. 같은 날 다른 새벽 이벤트까지 정상이라고 판정하지 않는다.
- 자료를 하나만 고르면 부족한 비교 대상을 알려주고, 두 자료의 시각이나 runner가 다르면 다시 보게 한다.

### 단계별 힌트

1. “접근 시각과 계정 이름만으로 사용자의 로그인인지 알 수 없습니다.”
2. “Dolphin의 사건용 운영 기록에서 같은 시각의 작업 일정과 실행 결과를 비교하세요.”
3. “`svc-build`의 인증 방식, `nightly-build` 일정, `build-runner-02`의 실행 기록이 같은 작업을 가리키는지 확인하세요.”

### 세계관과 다음 임무

### 접근과 조작의 보장

- `dev-files.root.internal`의 `logs` 공유는 읽기 전용이며, 접근 주체는 관리형 워크스테이션의 Kerberos 세션으로 확인한다. 문서와 공유는 게임 내부에서 동작한다.

### 정답과 완료 조건

1. **확인된 사실:** 09/24 18:42의 정상 세션과 09/26 02:14의 세션은 계정·서비스가 같지만 source와 시각 패턴이 다르다.

보고서에서는 정상·의심 로그, 자동 작업을 확인한 기록, 공개 기록 하나를 **증거 보관함에서 선택**한다. 시간·계정·출처는 선택된 기록에서 자동 채우고, 플레이어는 차이점과 판단의 한계를 짧게 설명한다. 현재처럼 특정 날짜·호스트 문자열을 자유 서술에 포함해야만 통과시키는 검사는 없앤다.

## 7. 기존 구현에서 목표 설계로 옮기는 순서

1. **콘텐츠와 번호 확정:** 도입/001/002/003의 사건 ID를 명확히 정하고, 현재 `orientation-001`, `internal-access-002`와 새 ID의 대응표를 만든다. 기존 콘텐츠 팩은 MISSION 003의 자료 출처로 유지한다.
2. **진행 상태 이관:** 현재 `stage: 0|1|2`, `highestStage`, `mission002HintsUsed`, `report`는 새 3개 사건을 표현하기에 부족하다. 사건 ID별 배정·단계·증거·보고서·힌트를 저장한다. 기존 계정은 자동으로 가장 가까운 단계에 옮기되 완료된 보고서를 지우지 않는다. 이관 전후 상태를 테스트한다.
3. **001을 먼저 끝까지 연결:** 배정 → 모든 페이지 접근 → 증거 선택 → 제출 → 재접속 후 완료 유지까지 한 경로를 구현한다. 이후 002, 003 순으로 연다.
4. **자료와 검증을 같은 출처에 둔다:** 사건 fixture에 문서/페이지 ID, 정상 답, 허용 결론을 정의한다. 화면 텍스트와 서버 검증이 서로 다른 문자열에 의존하지 않게 한다.
5. **복구 경로 확인:** 오답 제출, 브라우저 새로고침, 앱 닫기, 다운로드 재시도, 임무 되돌리기, 다른 브라우저에서 접속하기를 각각 확인한다.
6. **README와 테스트 갱신:** 현재 README의 `첫 조사 사건 없음` 설명과 MISSION 002 기준 E2E를 새 순서에 맞춘다. E2E는 API로 완료 이벤트만 주입하지 말고, 최소한 001의 실제 화면 경로와 003의 핵심 도구 경로를 확인한다.
